# ent data layer

`agent-compose` supports SQLite (the default) and PostgreSQL. Both backends are
opened and migrated by `pkg/storage/database`; the released SQL files under
`pkg/storage/sqlite/migrations` and `pkg/storage/postgres/migrations` remain the
only source of the physical schema. ent is the typed data-access layer on top of
those tables.

```
ent/
├── schema/       handwritten model of every released table
├── dao/          GENERATED by entc — never edit
├── entc/         generator command (run through `task generate:ent`)
├── helper/       ent transaction helper
└── generate.go   `go:generate` hook
```

## Source-of-truth boundary

| Concern | Owner |
|---|---|
| Physical tables, columns, indexes, defaults, primary keys | `pkg/storage/{sqlite,postgres}/migrations` |
| Go model of those tables, used by every store | `ent/schema` |
| Typed query/mutation API | `ent/dao` (generated) |

The runtime never runs ent's automatic migration (`dao.Client.Schema.Create`).
Existing data roots are upgraded only by the released migration chains, and they
must keep working without a data rewrite. Because of that:

- `ent/schema` mirrors the physical schema one-to-one. `pkg/storage/database/ent_schema_test.go`
  fails when an entity, field, storage key, primary key, or Optional/default
  marker drifts from the migrated SQLite schema.
- `pkg/storage/postgres/schema_parity_integration_test.go` covers the other half:
  the SQLite and PostgreSQL chains must produce the same table/column/index
  shape.
- ent edges are intentionally not declared. Foreign keys are enforced by SQL, and
  several relationships use composite keys ent cannot model as edges.

## Changing the model

1. Edit `ent/schema` (never `ent/dao`).
2. If the change touches the persisted shape, add the paired SQL migrations in
   `pkg/storage/sqlite/migrations` and `pkg/storage/postgres/migrations` with the
   same six-digit version and name. Data rewrites that are clearer in Go belong
   in a versioned data step next to the SQLite runner. Never edit a released
   migration.
3. Run `task generate:ent` and commit the regenerated `ent/dao`.
4. Run `task check:ent`, `go test ./pkg/storage/...` (plus the PostgreSQL
   integration tests when a test database is available).

`task generate:ent` requires the Go toolchain declared by `go.mod` (currently
1.26.x). ent v0.14.6's schema loader depends on `golang.org/x/tools`; the module
pins a version that can read export data produced by newer toolchains as well,
but the supported build toolchain is the one in `go.mod` and CI.

ent's Atlas-based migration generator is deliberately not used: the project ships
two paired, checksummed SQL migration chains for existing deployments and does
not apply DDL from the Go model. Any generated DDL would still have to be
reviewed and landed as a paired migration, so the ent tooling would add a third
source of truth rather than remove one.

## Writing queries

- Use the generated client for single-table reads, writes, upserts, deletes, and
  affected-row checks. Stores already hold a shared `*dao.Client`; build it with
  `dao.NewClient(dao.Driver(entsql.OpenDB(dialect.EntDialect(), db)))`.
- Composite primary keys: ent has exactly one ID field per entity, mapped to the
  first key column. The schema comments mark those entities; never call
  `UpdateOneID`/`DeleteOneID` on them, and constrain every key column with
  predicates.
- Fields that rely on a database default are `.Optional()` in the schema, so a
  `Create` omits them exactly like the released `INSERT` did. Set a field when
  the old statement set it, even to its zero value.
- Keep SQL for read models ent cannot express without changing semantics —
  joins, aggregates/`CASE`, CTEs/windows, row locks, migrations, and bulk copy.
  Mark each kept statement with `// Kept as SQL: <reason>` so the remaining
  handwritten SQL stays visible in review.

## Adding a store method

1. Add the field/entity to `ent/schema` if the model changed and regenerate.
2. Query through the ent client, or use `ent/helper.WithTx` when several
   statements must commit together.
3. Map rows to domain types with a `<entity>FromEntity` function next to the
   store; keep JSON decoding, timestamp units, identity fallbacks, and
   normalization identical to the previous scanner.
4. Map ent's `dao.IsNotFound` and duplicate-key errors back to the store's
   existing `domain.ResourceError` classification instead of leaking ent errors.
